### 2. Отработка потенциальных возражений  

| № | Возражение | Ответ (ключевые тезисы) |
|---|------------|--------------------------|
| **1** | **Техлид Fast Cargo:** *«Временное решение для DWH создаст риски для стабильности текущих отгрузок и потребует переписывания легаси‑кода»* | 1. **CDC‑подход** (Debezium) **только читает** WAL‑лог; никаких `INSERT/UPDATE` в монолит не производится. <br>2. Репликация происходит в отдельный процесс‑консюмер, который работает на отдельном кластере Kafka → ClickHouse – нагрузка на транзакционный узел **≈ 0 %**. <br>3. Пилотный запуск в *blue‑green*: сначала **read‑replica** (green) обслуживает только аналитические запросы, монолит (blue) остаётся на обслуживании отгрузок. Переключение триггерится двумя условиями — **оба** должны выполняться 5 мин подряд: <br> - p95 `ch_query_time` green‑контура ≤ 1.5× baseline blue; <br> - Текущее `p95(write_latency)` за 5-мин окно не превышает **7-дневный rolling baseline p95 × 1.25** (т.е. допустимо +25% деградации от исторического уровня; порог выбран так, чтобы лежать выше 7-дневной естественной вариации baseline 10–15%, но ниже уровня, при котором транзакции реального потока теряют SLA 500 мс). <br> **Дополнительно** (AND-условие, любой триггер → rollback):<br> - `deadlock_rate > 0.05%` (5-мин окно) — ловит lock-contention, который не всегда виден в latency-перцентилях; <br> - `statement_timeout_error_rate > 0.01%` — ловит деградацию, которая уже переросла во failures; <br> - **absolute floor**: `p95(write_latency) > 500 мс` — независимо от baseline, это красная линия транзакционного SLA. <br> **Почему не p99:** write-latency в PostgreSQL heavily right-skewed (fsync-очереди, vacuum interference, lock waits). 7-дневный baseline по p99 даёт ±60% noise, что делает любой σ-pipeline бесполезным. p95 стабилен при ±10–15% baseline variance, что соответствует порогу деградации.<br> **Почему не абсолютный порог в мс:** baseline write-latency на SSD/NVMe ~2–5 мс p50, ~30–80 мс p95 в healthy state, но дрейфует с ростом БД, числом индексов, размером WAL. Относительный порог к baseline учитывает дрейф, абсолютный — нет. <br> - **Авто‑откат** (rollback to blue) запускается при нарушении любого условия в течение 5‑мин окна, оператор вмешивается только если rollback сам не прошёл (rare). Формальный 0‑downtime гарантируется именно этой схемой: переключение — это смена view в Grafana/ETL,а не рестарт приложения. |
| **2** | **Отдел ИБ «Плюс Ритейл»:** *«Интеграция CRM нарушает требования 152‑ФЗ, так как персональные данные лежат в общем контуре монолита»* | 1. **CustomerProfile microservice** хранит ПД в отдельной базе с шифрованием **AES‑256**; доступ к ней только через сервисный слой с **RBAC**. <br>2. **Data flow PAN (где PAN физически не появляется):** TLS 1.3 / 256-bit -> Payment‑Proxy (ephemeral RAM only) -> PAN → token (AES‑256, key in HSM) -> Token (opaque 36‑char UUID) ──→ Kafka ──→ PostgreSQL -> CRM (только token) ClickHouse (только token) <br> **Гарантия:** PAN не попадает **ни** в PostgreSQL (там колонки `pan` нет в schema), **ни** в ClickHouse (ETL whitelist исключает PAN‑колонки), **ни** в логи (structlog + regex‑mask на границе Payment‑Proxy → все приложения), **ни** в Kafka‑headers (envelope schema без PAN‑полей, enforced через Avro registry). При утечке токена он бесполезен без HSM‑ключа; TTL токена = 60 мин, ротация — по событию `customer.token.rotate`. <br>3. Все операции журналируются в **OpenTelemetry**, а аудит‑лог хранится в отдельной базе, что упрощает проверку соответствия ФЗ‑152. |
| **3** | **Производственный департамент «Плюс Ритейл»:** *«Поток телематики IoT на 3000 RPS создаст цунами данных и мгновенно уронит текущую инфраструктуру и СУБД»* | 1. **IoT‑Bridge** использует **MQTT** ( lightweight ) → **Kafka** ( durable, horizontally scalable). С‑лой **Kafka** гарантирует **exactly‑once** доставку без влияния на основную СУБД. <br>2. Данные сразу записываются в **ClickHouse** (колоночный, оптимизированный под массовый ingest), а не в транзакционную PostgreSQL. <br>3. План тестирования под нагрузкой (10× ожидаемого RPS) будет проведён до продакшн‑переключения; если потребуется, мы масштабируем брокеры Kafka и узлы ClickHouse вертикально/горизонтально без простоя. |
| **4** | **Архитектурный штаб / CEO:** *«Почему мы сразу идём в микросервисы, а не делаем модульный монолит? Это дешевле и меньше рисков»* | 1. Модульный монолит решает проблему, когда 1–2 домена конкурируют за ресурсы внутри одного процесса. У Fast Cargo **5 доменов** (Заказы, Отгрузки, Клиенты, Платежи, IoT) уже конкурируют. <br>2. **Триггер декомпозиции** — как только в одном PostgreSQL‑ядре ≥ 3 write-тяжёлых транзакционных контура генерируют **concurrent row locks** на > 5% времени (измеряется через `pg_stat_activity` + lock graphs), модульный монолит не масштабируется дальше без физического разделения БД. Расчёт по текущему профилю нагрузки Fast Cargo показывает, что при переходе на 500 тыс. отгрузок/сутки этот порог преодолевается по 3 доменам одновременно. <br>3. **Дополнительный аргумент** — изолированные релиз-циклы: IoT-команда не зависит от релиза Отгрузок-команды. В модульном монолите все команды релизятся за одним координатором. <br>4. **Оговорка честности:** модульный монолит — допустимый шаг для проектов < 100 тыс. отгрузок/сутки и < 3 write-доменов. Для Fast Cargo на горизонте 12 месяцев — не проходит по двум из трёх критериев (объём + количество доменов). |
