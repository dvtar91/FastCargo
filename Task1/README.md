# План архитектурной трансформации Fast Cargo

## 1. Выгоды бизнеса

- Поддержать рост до 500 тыс. отправлений/сутки и пики 200 RPS создания заказов; рост выручки зависит также от спроса и физических мощностей логистики.
- Снизить простои: целевая доступность ядра ≥99,95% за год; исключить потери платёжных уведомлений из-за внутренних таймаутов.
- Предоставлять DWH холдинга ключевые статусы заказов не позднее чем через 5 секунд после фиксации изменения в источнике.
- Изолировать персональные и платёжные данные, обеспечить проверяемость требований ИБ и независимость релизов доменов.

## 2. Базовая и целевая архитектура

**AS-IS:** веб и мобильное приложение → общий BFF / FastAPI-шлюз → монолит Orders, Warehouse, Delivery, Finance → единый физический инстанс PostgreSQL. Общие таблицы, междоменные связи, тяжёлая отчётность и запись координат конкурируют за ресурсы; таймауты шлюза приводят к потере вебхуков. Главный антипаттерн — тесная связанность кода и данных.

**TO-BE за 12 месяцев:** совместимый API Gateway → независимые доменные сервисы Orders, Warehouse, Delivery, Finance; отдельные EDI Adapter, IoT Ingest, CustomerProfile, CRM Adapter и Payment Webhook. Database-per-Service: собственные физически изолированные БД/инстансы, отдельные учётные записи; чужие БД недоступны, междоменные JOIN и распределённые блокировки запрещены. Kafka переносит события; бизнес-команды проходят через API либо события с корреляцией. Это Event-Driven Architecture, без обязательного Event Sourcing. Читаемые проекции используются для CRM и аналитики.

**EDI:** ORDERS → проверка и резервирование Warehouse → подготовка/подтверждение отгрузки DESADV → выпуск INVOIC Finance. Saga хранит шаги и сроки; переход к счёту/оплате допускается только при подтверждённом резервировании и допустимом статусе отгрузки. При отказе — отмена заказа/освобождение резерва; после необратимой отгрузки — корректирующий документ и управляемое разбирательство. Transactional Outbox атомарно фиксирует состояние и событие в локальной транзакции; Inbox/event_id, idempotency key и версии агрегатов защищают от дублей и нарушения порядка. Retry с backoff, DLQ и сверка восстанавливают согласованность.

**IoT:** устройства с локальным буфером → MQTT с подтверждением после долговечного приёма → Kafka → GeoProcessor → отдельное аналитическое хранилище. ACK MQTT сам по себе не доказывает запись в Kafka: мост имеет долговечную очередь. Сбой склада/финансов не блокирует поток; для заказов, IoT и аналитики выделены квоты и ресурсы.

**ИБ:** паспорт, телефон и email переносятся в CustomerProfile на отдельном физическом хранилище. В доменах остаётся customer_id; UUID — псевдоним, а не доказательство обезличивания. CRM получает разрешённые сведения через OAuth2/mTLS, RBAC и аудит; аналитика получает только разрешённые обезличенные поля. PAN вводится исключительно в форму/виджет банка: банк токенизирует данные, Fast Cargo принимает подписанный webhook с payment_id и статусом. PAN не проходит через память, сеть, логи или очереди Fast Cargo.

## 3. Область применения

| In-scope | Out-of-scope |
|---|---|
| Декомпозиция BFF/монолита, миграция доменных данных и ПД; CDC/Kafka/DWH-интеграция; IoT, EDI, CRM и платёжные адаптеры; мониторинг и эксплуатация | Внутренняя реализация CRM, DWH, EDI и банковских систем партнёров; бухгалтерия/юриспруденция подрядчиков; замена физических складов и транспорта |
| Сохранение текущих API фронтендов через совместимый фасад; изменения платёжного интерфейса только при необходимости банковского redirect/widget | Полная переработка веб/мобильного UX и новые функции вне согласованных интеграций |

## 4. Ограничения и допущения

Промежуточный этап — 12 недель; полный демонтаж монолита — не позднее 12 месяцев. В первые 12 недель код легаси не меняется и аналитические SELECT к его бизнес-таблицам не добавляются. Административная настройка PostgreSQL для CDC разрешается отдельно в согласованное окно. Версия БД, возможность logical decoding и доступность резервной копии — проверяемые предпосылки, а не установленные факты.

Размещение — ЦОД холдинга либо согласованное Managed-облако с подходящими размещением данных и средствами ИБ. Применимые требования 152-ФЗ, ГОСТ и платёжного комплаенса определяет ИБ; шифрование не заменяет организационные меры. Предпочтительный стек: PostgreSQL, Kafka, Debezium, ClickHouse; Open Source обеспечивает контроль и переносимость, но требует компетенций и поддержки. Сравнение с коммерческими вариантами — по TCO, SLA поддержки, интеграциям и требованиям ИБ; лицензии проверяются до закупки. Kubernetes используется при подтверждённой готовности эксплуатации.

CAPEX/OPEX и состав команды фиксируются после аудита и согласования с финансовым блоком; вымышленные суммы не принимаются как бюджет. Предполагается доступность DBA, Data Engineer, Backend, DevOps/SRE и ИБ; при нехватке — обучение/подрядчик с включением затрат в TCO.

## 5. Transition Architecture: первые три месяца

| Уровень | AS-IS | Через 12 недель | GAP и место изменений |
|---|---|---|---|
| Data | Общая PostgreSQL и отчётные SELECT | WAL CDC → Kafka → изолированная аналитическая проекция → DWH; чтение отчётности перенесено | Нет независимой аналитики: replication slot/publication, коннектор, обезличивание и DWH ingestion |
| Apps | Монолит и общий шлюз | Монолит и клиентские API сохранены; интеграционный pipeline работает отдельно | Нет контракта событий: mapping CDC, event_id, schema и сверка; без правок легаси |
| Infra | Один физический инстанс БД; топология приложений уточняется | Отдельные ресурсы pipeline, резервирование, мониторинг WAL/диска, квоты | Нет ресурсной изоляции: ЦОД/согласованное облако, сеть и эксплуатационные настройки |

## 6. Обоснование переходного решения

CDC читает изменения через logical decoding. Initial snapshot бизнес-таблиц отключён: для проверенной версии Debezium используется `snapshot.mode=no_data` либо документированный эквивалент. Служебные запросы к метаданным и replication protocol не являются аналитическим чтением бизнес-таблиц; если запрет охватывает и их, запуск блокируется до согласования трактовки. История загружается из существующей резервной копии в отдельный staging. DBA обязан проверить согласование копии и позиции CDC: слот создаётся до выбранной согласованной точки копирования, WAL удерживается, повторные изменения дедуплицируются по ключу/версии. При отсутствии пригодной копии/позиции полная история не обещается: способ bootstrap согласуется до запуска.

Разрешённые таблицы/поля заданы allowlist; ПД исключаются до публикации в аналитическую Kafka. Source LSN, ключ, операция и версия позволяют применить INSERT/UPDATE/DELETE и повторы. В ClickHouse выбирается модель актуального состояния с версиями и tombstone; агрегаты строятся по дедуплицированному состоянию, а не суммированием всех CDC-записей. Timestamp источника и момент доступности в DWH определены контрактом; часы синхронизированы. CDC не создаёт аналитических SELECT, но потребляет CPU/I/O и удерживает WAL: влияние измеряется, нулевая нагрузка не обещается.

## 7. Дорожная карта, риски и переключение

| Пакет | Срок | Работы и ответственность |
|---|---|---|
| Аудит и согласование | Недели 1–2 | Архитектор/DBA/ИБ: baseline, CDC/bootstrap, поля, размещение и бюджет |
| Инфраструктура | Недели 3–5 | DevOps/SRE: Kafka, staging/DWH, сеть, резервирование и наблюдаемость |
| Pipeline и проверки | Недели 6–9 | Data Engineer/DBA: CDC, обработка изменений, обезличивание; нагрузочные и отказные испытания |
| Приёмка DWH | Недели 10–12 | Data Engineer/Ops: 14 суток наблюдения, сверка и переключение потребителей аналитики |
| Изоляция и сервисы | Месяцы 4–6 | Backend/ИБ: CustomerProfile и платежи; Orders/Warehouse, Outbox и Saga |
| Интеграции | Месяцы 7–9 | Integration/Backend: EDI, IoT, Delivery/Finance, CRM; проверка сквозных сценариев |
| Завершение | Месяцы 10–12 | Ops/владельцы доменов: миграция данных, переключение API, сверка; отключение монолита после приёмки |

**Риски и откат:** при росте WAL/дефиците диска или деградации записи сначала остановить переключение и потребителей аналитики, сохранив offsets; восстановить pipeline до исчерпания согласованного WAL-запаса. Слот не удаляется без решения DBA: при утрате WAL требуется повторный bootstrap и сверка. Переключение аналитики откатывается к прежней конфигурации без новых SELECT к production; при необходимости отчёты временно доступны с отметкой устаревания. Для сервисов откат маршрутизации возможен только после сверки новых записей и синхронизации старого контура; Git rollback не восстанавливает данные. IoT не отключается без долговечного буфера и последующего replay.

**Приёмка на 12-й неделе:** ключевые статусы доступны в DWH ≤5 с, число нарушений регистрируется; p95/p99 — диагностические показатели, а не разрешение превышать SLA. Нет необъяснённых пропусков/дублей, UPDATE/DELETE и replay проверены; запрещённые ПД отсутствуют. p95 записи монолита не превышает baseline более чем на согласованный порог (предварительно 10%) и исходный SLA; запас диска/WAL достаточен для согласованного отказа. После 14 суток проверки — резервная точка, переключение аналитических потребителей, контроль и готовый откат. Годовая приёмка дополнительно подтверждает 500 тыс./сутки, 200 RPS, IoT 3000 сообщений/с, доступность и восстановление платежей.
